# SLAP FLASH verification and recovery

The versioned 0.1.0 package is an unpublished engineering candidate. No release manifest is staged. Do not flash it. The previous 611,496-byte development package included the 602,112-byte flash image, loader and envelope. Neither its total size nor the app binary alone describes what is erased. The updated package audit records the current sizes and SHA-256 values.

The pinned SDK hashes are recorded in sdk.sha256. tools/audit-package.py reconstructs the package from the pinned inputs, compiled app and compiled loader, then compares complete bytes. The browser validates size, SHA-256, product, UFW header and entry CRCs, exact entry types and layout, outer and inner loader headers, loader staging capacity, CRCs, and loader marker. A missing or invalid manifest leaves installation disabled.

The upstream USB MIDI SysEx pull protocol is used with one connected input and output, an exact source firmware allowlist, and a fresh identity probe before staging begins. Progress reports bytes and requests actually served. Completion requires the device to reappear under the target product identity. The app-area loader additionally rejects anything except the source-baseline 1 MiB JEDEC part 856014 before any app erase and verifies the chip key and image before writing. The loader targets [0x4000,0x93000) and verifies changed sectors by readback. The boot area is outside that write window. Staging and valid update-record cleanup use separate higher flash sectors. A MIDI firmware identity alone cannot attest the bootloader or flash device. Physical verification of both is required before qualifying a release and publishing its manifest. Stock V16 and other flash IDs are excluded by the current conservative installer policy.

If a later qualified update is interrupted, record the on-device message and identity and use the supported recovery mode and the exact backup for that unit. Do not substitute a package from another bootloader revision. In a recovery session that no longer answers over MIDI, consult the manufacturer's recovery procedure and the FM-1 Developers' Wiki. A release requires a device-backed test of the complete staging/reboot/transfer/reboot path and recovery from interruption, plus audio timing acceptance.
